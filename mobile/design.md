# تصميم تطبيق Delivery Tartous Native

## الهدف

ينقل تطبيق React Native تصميم وتجربة تطبيق Delivery Tartous الحالية إلى الموبايل من دون تغيير منطق الأعمال أو قواعد Supabase. التصميم مخصص للشاشات العمودية بنسبة 9:16، ويدعم العربية واتجاه RTL منذ الجذر، مع مساحات لمس مناسبة للاستخدام بيد واحدة.

## شاشة الأساس والتنقل

تظهر شاشة Launch مختصرة أثناء تهيئة الجلسة. بعد ذلك يحدد الدور التجربة: Admin وSupervisor يستخدمان هيكل Back Office، بينما Captain يستخدم هيكل تشغيل ميداني. كل شاشة تقع داخل Safe Area، ويظهر زر رجوع في رأس الشاشة فقط عندما يكون هناك مسار سابق. عند عدم وجود مسار سابق، يعود المستخدم إلى الرئيسية المناسبة لدوره.

| الهيكل | الشاشات الأساسية | التنقل |
|---|---|---|
| Auth | تسجيل الدخول، تفعيل الحساب | Stack بدون Bottom Tabs |
| Admin | الرئيسية، الطلبات، المستخدمون، الأجور، المزيد | Bottom Tabs مع Stack للتفاصيل |
| Supervisor | الرئيسية، الطلبات، الكباتن، الأجور، المزيد | Bottom Tabs بصلاحيات Supervisor |
| Captain | الرئيسية، الطلبات، الأجور، الإعدادات | Bottom Tabs للتشغيل الميداني |

## قائمة الشاشات

| الشاشة | المحتوى والوظيفة |
|---|---|
| Login | بريد وكلمة مرور، حالات التحميل والخطأ، استرجاع الجلسة دون وميض |
| Activate Account | إكمال تفعيل حساب Pending ثم الانتقال حسب الدور |
| Home | ملخصات مباشرة حسب الدور، نشاطات مختصرة، وإجراءات سريعة |
| Orders | FlatList للطلبات، فلاتر الحالة، Pagination، تعيين الكابتن وتغيير الحالة |
| Order Detail | بيانات العميل، نقاط المصدر والوجهة، الحالة، وتأكيدات الأفعال الحساسة |
| Users | الحسابات المفعلة والمعلّقة، إنشاء حساب، أدوار وحالة الكابتن حسب الصلاحية |
| Captains | قائمة الكباتن وتوفرهم وبياناتهم التشغيلية |
| Wages | فترات يومية/أسبوعية/شهرية، إجماليات، كشف الكابتن والدفعات |
| Captain Home | التوفر، الطلبات النشطة، المقاييس اليومية |
| Captain Orders | قائمة العمل، تفاصيل الطلب، الانتقالات المسموح بها فقط |
| Captain Wages | ملخص الأجر والكشف الشخصي |
| More / Settings | إعدادات المكتب أو الحساب، المساعدة، وتسجيل الخروج |

## تدفقات المستخدم الرئيسية

1. يسجل المستخدم دخوله، ثم يستعاد Profile مرة واحدة، ويُوجّه تلقائياً إلى هيكل الدور الصحيح.
2. يفتح Admin طلباً من القائمة، يعيّن Captain عبر Modal، ثم يتابع حالة الطلب من التفاصيل.
3. يبدّل Captain حالته إلى متاح، يفتح طلبه، ويؤكد الانتقال التشغيلي المسموح فقط.
4. يفتح Admin الأجور، يختار الفترة، يقرأ الأرقام من RPC، ثم يفتح كشف كابتن عند الحاجة.
5. يستخدم المستخدم زر الرجوع في الرأس للعودة إلى السياق السابق، أو Bottom Tabs للانتقال إلى جذر القسم.

## أسلوب الواجهة والألوان

تستخدم الواجهة هوية Delivery Tartous الحالية: الأزرق التشغيلي كلون رئيسي، خلفية زرقاء باهتة، أسطح بيضاء، ونص كحلي واضح. لا تستخدم أحجاماً ثابتة معتمدة على جهاز واحد؛ تعتمد Flex وSafe Area وFlatList.

| Background | `#EAF5FF` | خلفية الشاشات |

## مرجع المطابقة: Home الإداري

تُبنى Home الإدارية Native وفق المرجع الحالي في الويب، لا كتصميم بديل. تبدأ بهيدر ثابت بارتفاع صغير: الحساب والإشعارات في طرف، اسم «دليفري طرطوس» في المنتصف، وزر دعم في الطرف المقابل. بعده تظهر بطاقة ترحيب شفافة بيضاء بعنوان «مرحباً، المدير» ونص حركة اليوم.

تأتي المقاييس كبطاقات ثنائية الأعمدة: بطاقات بيضاء لحالات الطلب العادية، وبطاقة `in_delivery` مميزة بتدرج أزرق. كل بطاقة تفتح قائمة الطلبات بالفلتر نفسه الموجود في الويب. يليها زر «إنشاء طلب جديد» الكبير بتدرج أزرق وصورة توضيحية منخفضة الشفافية، ثم قسم «آخر النشاطات» كبطاقات بيضاء ذات شريط حالة أيمن وزر انتقال، ثم صف الكباتن المتاحين بدوائر الاسم ونقطة توفر خضراء.

| عنصر الويب | المقابل Native | السلوك الذي لا يتغير |
|---|---|---|
| Header ثابت | `View` أعلى Safe Area | الحساب، التنبيه، الدعم، وهوية التطبيق بنفس الترتيب البصري |
| شبكة المقاييس 2×2 | `FlatList` ثنائي الأعمدة أو صفوف `View` | فتح Orders بفلتر الحالة نفسه، لا أرقام محلية |
| زر إنشاء طلب | `Pressable` كبير + Bottom Sheet | يتطلب كابتناً متاحاً، ويحافظ على idempotency وإنشاء/تعيين الويب |
| آخر النشاطات | `FlatList` | اللون والشريط والحالة والانتقال إلى تفاصيل الطلب نفسها |
| الكباتن المتاحون | `FlatList` أفقي | نفس مصدر التوفر وواجهة النقطة الخضراء |

## مرجع المطابقة: Login وتفعيل الحساب

شاشتا الدخول والتفعيل تستخدمان Auth Shell الويب نفسه: عنوان كبير في أعلى البطاقة، subtitle مختصر، حقول بيضاء بارتفاع واضح وحدود `#AEBBC5`، أيقونة الحقل على اليمين، وزر أساسي أزرق كامل العرض بارتفاع ثابت مع ظل خفيف. لا توجد شاشة إنشاء حساب عامة؛ زر «تفعيل حساب جديد» يفتح تفعيل Pending account موجود مسبقاً فقط.

| الشاشة | العناصر المطابقة | المنطق المطابق |
|---|---|---|
| Login | العنوان «مرحباً بعودتك»، البريد، كلمة مرور مع زر إظهار/إخفاء، زر دخول، رابط «تفعيل حساب جديد» | تحقق البريد وكلمة المرور، مهلة 15 ثانية، ثم Profile/role validation من Session Provider |
| Activate Account | العنوان «تفعيل حساب جديد»، البريد، كلمة المرور، التأكيد، زر التفعيل، عودة إلى Login، ملاحظة الحساب المضاف مسبقاً | كلمة مرور 12 حرفاً على الأقل، تأكيد مطابق، RPC `activatePendingAccount` ثم تسجيل دخول واستعادة Profile |
| أخطاء Profile في Login | بطاقة amber داخل Auth Shell وزر «إعادة المحاولة» | لا تعاد محاولة تسجيل الدخول ولا يمسح المستخدم Session سليمة عند تعذر قراءة Profile مؤقتاً |

## قواعد Native العامة

- جميع المحتوى يستخدم `ScreenContainer` وSafe Areas.
- كل قائمة بيانات تستخدم `FlatList` مع key ثابت وPagination حقيقية.
- الأزرار تستخدم `Pressable` مع مساحة لمس 44px على الأقل وحالة pressed واضحة.
- لا يوضع `className` على `Pressable`؛ تستخدم `style` للتفاعل.
- كل Modal يحتوي زر إلغاء وإجراء واضح، خصوصاً تغيير الحالة والدفعات والحذف مستقبلاً.
- لا توجد أرقام Mock؛ حالات التحميل والفراغ والخطأ تظهر من البيانات الحقيقية.
